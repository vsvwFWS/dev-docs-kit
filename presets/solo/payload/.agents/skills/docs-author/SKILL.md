# 開発ドキュメントの作成

## 作成前の判断

`docs/index.md` と `docs/_conventions.md` を読み、関連文書と用語集を確認します。同じ説明がある場合は正本を更新するかリンクし、重複文書を増やしません。

文書化は外部から見える振る舞い、重要な制約・判断、繰り返し使う手順を優先します。軽微な修正にspec・ADR・planを一式作る必要はありません。

- 現行の振る舞い・条件 → spec
- 新機能や仕様変更の案・実装と検証の作業 → plan
- 選択肢を比較した重要な判断 → adr
- 構成・責務・境界 → architecture
- 実行手順 → guide、調査結果 → note
- 目的と機能一覧 → overview、用語と識別子 → glossary

## 執筆

`docs/_templates/` の対応テンプレートを使い、配置・ID・状態は規約に従います。未確認の初版はdraftにします。採用したADRをacceptedにすることと実装完了は別です。

- 冒頭に対象・要点・適用範囲を書き、本文には利用例・根拠・例外を具体的に記述します。
- 未確認事項は本文に表示します。空欄を埋めるために推測を確定事項にしません。
- 該当しない項目・例を削除します。分割時は親に全体像を残します。
- summaryは200文字以内の具体的な要約に置き換えます。日付は当日、同じ機能のtagsは既存表記を再利用します。
- 文脈に沿った参照は本文の相対リンク、補足的な関係はrelatedに置きます。二重登録は不要です。
- ADRは既存の最大番号+1を4桁で採番します。判断の変更は新ADRのsupersedesで旧IDを指定します。採用時に旧ADRのstatusをsupersededへ変更し、本文は維持します。

## 読む入口と検証

存在する文書だけを使い、indexの自動生成範囲の外に目的別の読む順序を整えます。機能specを作ったらoverviewの機能一覧に接続し、specから必要なADR・guideへ進めるようにします。

```bash
node .agents/skills/docs-sync/scripts/docs_lint.mjs --index
```

エラーを解消し、作成文書・根拠・未確認事項を報告します。Lint成功を内容の検証済みという意味では使いません。
