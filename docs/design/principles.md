# PKM・Wiki 由来の開発ドキュメント整理原則

AIコーディングエージェントと人間の双方が迷わず読み書きできる開発ドキュメントを維持するため、PKM（Personal Knowledge Management：Zettelkasten、Obsidian 等）や技術文書フレームワーク（Diátaxis）のエッセンスを開発向けに再構成しています。

---

## 人間とAIが共有する文書の品質

人間が全体像・現行仕様・設計理由・予定変更を読み分けられることを目標にします。ビューアーはフロントマター編集・検索・分類・関係表示を補助し、Markdownを正本として維持します。

- indexの手書き案内から目的別に読む。overviewの機能一覧からspec、specからADRやguideへ進む。
- 必要な文書だけ増やす。軽微な修正ごとに一式を要求しない。
- specは現在有効な合意済み仕様、planは変更案と実装・検証結果を扱う。
- 同期時は合意済み変更・実装の不具合・意図不明を区別する。実装へ無条件に仕様を合わせない。
- 下書きと未確認事項は表示で区別する。Lintは構造、AIは根拠と差分、人間は意図と理解しやすさを確認する。
- 新規では入口・目的から、既存では正本の整理から始める。対象外一覧で段階的に移行する。

## 1. MOC（Map of Content）と段階的開示（Progressive Disclosure）

AIエージェントのコンテキストウィンドウは有限であり、無関係なドキュメントを大量に読み込むと推論精度の低下やコスト増大を招きます。人間にとっても、フォルダ階層だけを頼りに目的の仕様を探すのは負担になります。

- **解決策**:
  - `docs/index.md` を全ドキュメントの目次ハブ（MOC）として配置します。
  - 目次の冒頭に目的別の手書き案内を保持し、現行・下書き・進行中を分け、履歴は別ページに集約します。
  - 各ドキュメントの YAML フロントマターに 1〜2 文の `summary` を必須化します。
  - `docs/index.md` には `- [タイトル](パス) — summary` の形式で一覧を掲載し、エージェントはまず `index.md` だけを読んで、作業に必要なファイルだけを選択的に開きます。

## 2. Atomic Notes（1ファイル1テーマ）

1つの巨大な設計書に全機能の仕様や設計判断を詰め込むと、以下の問題が起きます。
- AIが一部だけを参照・編集しづらく、無関係な箇所まで書き換えてしまうリスクがある
- Git の差分（diff）が大きくなり、レビューしづらい

- **解決策**:
  - 機能仕様は `docs/specs/<feature>.md`、設計判断は `docs/adr/NNNN-<slug>.md` のように **1ファイル1テーマ** に分割します。
  - `architecture.md` などの全体文書も、1つのセクションが肥大化（目安として文書全体で 300 行超）したら分割を検討します。分割後も親文書に全体像の要約を残します。

## 3. Evergreen（長期資産）と Fleeting（一時文書）の分離

「現在の正しい仕様」と「作業中のタスク計画や試行錯誤のメモ」が混在すると、AIが古い計画書を現行仕様と誤認して実装してしまう事故が起きます。

- **解決策**:
  - **Evergreen（長期維持）**: `overview`, `architecture`, `glossary`, `spec`, `guide` — 合意した変更の実装・検証後に現行情報へ更新します。不具合に合わせて仕様を変更しません。
  - **Immutable（不変の記録）**: `adr`（Architecture Decision Record）— なぜその設計を選んだかの歴史的記録。一度 `accepted` になった ADR は原則書き換えず、方針変更時は新しい ADR を作って `supersedes` で旧 ADR を指します。
  - **Fleeting（一時文書）**: `plan`（作業計画）— 完了したら `status: done` にして `docs/plans/archive/` へ移動し、進行中の計画と明確に区別します。

## 4. Diátaxis を参考にした文書タイプの役割分担

「何をどこに書くか」で迷わないよう、文書の性質ごとに `type` を分けています。

| 分類 | 対応する `type` | 目的 |
|---|---|---|
| **全体像・入口** | `index`, `overview` | プロジェクトの目的・スコープと全文書の案内 |
| **Explanation（背景・構造・理由）** | `architecture`, `adr` | システム構造の理解と、設計判断の理由 |
| **Reference（正確な定義・仕様）** | `glossary`, `spec` | 用語定義、機能ごとの要件・受け入れ条件・I/F |
| **How-to（手順）** | `guide` | 環境構築、デプロイ、運用手順 |
| **Working Memory（作業計画・知見）** | `plan`, `note` | 実装ステップの進行管理、技術調査やハマりどころの記録 |

## 5. 安定した ID による関連付けと標準 Markdown リンク

PKM ツールでは `[[wikilink]]` がよく使われますが、VSCode の標準プレビューや GitHub 上ではリンクとして機能しないことがあります。一方、ファイルパスだけで関連を管理すると、ファイル移動やリネーム時にグラフ構造が壊れやすくなります。

- **解決策**:
  - **本文中のリンク**: どの環境でも確実に機能する **相対パスの標準 Markdown リンク**（例: `[ログイン仕様](../specs/login.md)`）を使用します。
  - **メタデータ上の関連付け**: フロントマターに不変の `id`（例: `spec-login`, `adr-0001`）を持たせ、関連文書は `related: [spec-login]` のように ID で参照します。
  - **逆リンク（Backlinks）の自動算出**: 本文リンクはreferenceBacklinks、relatedは既存のbacklinksとして計算します。二重登録や逆リンクの手書きは不要です。型付きedgesでrelated・references・supersedesを区別します。
